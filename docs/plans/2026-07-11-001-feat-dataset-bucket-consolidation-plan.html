Summary

A dataset preprocessing tool — accessible from the dataset detail page — that scans image dimensions, shows the current bucket distribution, lets the user pick a target resolution and operation mode (resize-only or crop-to-ratio), optionally uses the configured vision LLM to detect the focal point of each image that needs cropping, then presents a per-image review grid where crop anchors can be overridden before the final Pillow-based processing run that writes output to a new sibling dataset folder.

Motivated by training runs where a dataset's images spread across many aspect-ratio buckets — e.g. a mix of 16:9 video exports, 1:1 product shots, and 3:4 portraits — causing the trainer to maintain many small per-bucket batches, slowing caching and reducing effective batch size. Consolidating to one or two target buckets fixes this without sacrificing important image content, provided the crop is guided by where the subject actually sits in the frame.

Reference implementation: github.com/mnslarcher/resize-and-crop-for-bucketing — MIT-licensed, uses the same resize-then-center-crop approach. We borrow the crop math and add anchor offset support + vision LLM guidance on top.

Problem Frame

When a dataset's images have varied aspect ratios, the ai-toolkit trainer creates a separate latent bucket for each distinct WxH output resolution. A dataset with 200 images spread across 12 buckets means some buckets have <20 images, making per-bucket batches tiny and VRAM efficiency low. The AI Config Check already detects and flags this; this tool closes the loop by fixing it.

The naive fix — center-crop everything — risks cutting off the subject. A portrait with the person on the left side of a wide frame becomes headless after a center crop. The correct fix is to know where the subject is and crop from the opposite side.

Constraints that shape the solution:

  • Must be non-destructive (new folder, never touch originals)
  • Must work independently of whether a training job has been run (no dependency on Job.dataset_stats)
  • Must use ai-toolkit's own bucket algorithm (toolkit/buckets.py) to guarantee output images land in the expected training bucket
  • Vision LLM calls are slow per-image; progress must be streamed
  • The tool should be usable without any LLM configured (falls back to center crop + user override)

Key Technical Decisions

DecisionChoiceRationale
KTD-1: Image dimension scanning Python script via spawn(resolvePythonPath(), ...) — same pattern as /api/scripts sharp is not installed in the project. The Python venv has PIL, and toolkit/buckets.py is importable from the toolkit root. A scan script avoids adding a new Node dependency and reuses existing Python infrastructure. Script placed in ui_scripts/ so the existing /api/scripts route can invoke it directly.
KTD-2: Bucketing algorithm toolkit.buckets.get_bucket_for_image_size(w, h, resolution, divisibility=8) — the trainer's own function Must match what the trainer does at training time to guarantee that output images land in the intended bucket. The mnslarcher reference script uses a different approach (all-combos → closest aspect ratio, divisible_by=64). Using the trainer's function directly avoids any bucket mismatch.
KTD-3: Crop math Borrow mnslarcher's resize-then-crop approach; replace the hardcoded // 2 center offset with * anchor_factor The reference implementation's crop logic is correct and well-tested: resize so the short side matches the target, then crop the excess from the long side. We parameterise the crop offset: anchor 0.0 = crop from far end, 0.5 = center, 1.0 = crop from near end. The 3×3 grid maps to (anchorX, anchorY) pairs — e.g. top-left → (0.0, 0.0), center → (0.5, 0.5), bottom-right → (1.0, 1.0).
KTD-4: Focal point detection transport New SSE route POST /api/datasets/focal-points using ReadableStream + text/event-stream Focal point detection calls the LLM in Node.js (using the already-installed openai SDK with the configured Ollama endpoint). SSE is the right transport for per-image progress since it's a long-running server push. The client reads the stream via fetch() + response.body.getReader(). Not using /api/scripts for this — the LLM calls are Node-native and shouldn't go through Python.
KTD-5: Crop preview overlay CSS clip-path polygon "hole" approach — one div with a clip-path that cuts out the kept region, revealing the image with darkened surroundings Pure CSS, no canvas, no extra libraries. The kept-region rectangle is expressed as a percentage of the thumbnail dimensions. A single absolutely-positioned overlay with clip-path: polygon(outer-rect, inner-hole) darkens the discarded regions without touching the image element.
KTD-6: Processing script ui_scripts/crop_resize_dataset.py — invoked via /api/scripts with stream: true (NDJSON) The existing /api/scripts route already provides buffered + streaming Python execution with NDJSON output. The crop/resize script accepts a JSON file path for per-image decisions (anchor + mode), reads it once at startup, then processes each image and emits a progress NDJSON line. Using /api/scripts avoids duplicating the subprocess + stream plumbing.
KTD-7: Modal UX structure Single multi-step modal, 5 named steps: Scan → Configure → Detect → Review → Process/Done Keeps all state in one component and one place. Step skipping is clean: resize-only mode jumps from Configure directly to Process, skipping Detect and Review. A separate modal for the review grid would require passing a large decisions object between modals.
KTD-8: Output folder naming {datasetsRoot}/{datasetName}_bucket_{W}x{H}/ Unambiguous, sortable, reveals the target bucket at a glance. If a same-named folder already exists, append _2, _3, etc. — checked by the processing API route before spawning the script.
KTD-9: Caption file handling Python script copies all sidecar files (.txt, .json, .caption) alongside each processed image A processed image without its caption is useless for training. Copying all three caption extensions covers every captioning workflow the UI supports without requiring the user to specify which one they used.

Implementation Units

U1 Bucket scan — Python script + API route

Goal

Scan all images in a dataset folder, compute each image's dimensions via PIL, determine its bucket at a given resolution using ai-toolkit's own algorithm, and return the distribution as JSON.

Dependencies

None — first unit to build.

Files

  • ui_scripts/scan_dataset_buckets.py
  • ui/src/app/api/datasets/[datasetName]/scan-buckets/route.ts

Approach

Python script (ui_scripts/scan_dataset_buckets.py):

  • CLI args: --dataset-dir PATH, --resolution INT (default 1024), --divisibility INT (default 8)
  • Scans dataset-dir recursively for .png .jpg .jpeg .webp files (same extensions as listImages route)
  • For each image: open with PIL, read image.size, call get_bucket_for_image_size(w, h, resolution, divisibility) from toolkit.buckets (importable since cwd is TOOLKIT_ROOT)
  • Accumulates {images: [{path, width, height, bucket_w, bucket_h, needs_crop}], buckets: {WxH: count}} where needs_crop is true when the image's aspect ratio differs from the target bucket's aspect ratio beyond a small tolerance (meaning a crop, not just a resize, will occur)
  • Emits the result dict as the final line of stdout (JSON) — compatible with the existing parseResult function in /api/scripts
  • Uses Image.open(...).size only (no decode) for speed; PIL lazy-loads image data

API route (POST /api/datasets/[datasetName]/scan-buckets):

  • Body: {resolution: number, divisibility?: number}
  • Resolves dataset path via getDatasetsRoot()
  • Spawns resolvePythonPath() directly (same pattern as /api/scripts runBuffered), passing --dataset-dir and --resolution
  • Returns the parsed result field from the script output (the JSON dict)
  • Timeout: 60 s (datasets should scan in <5 s even at 1000 images)

Patterns to follow

ui/src/app/api/scripts/route.ts — runBuffered function and parseResult. ui/src/app/api/datasets/listImages/route.ts — path resolution pattern.

Test scenarios

  • Dataset with 10 images, all 1024×1024: single bucket 1024x1024, count=10, no image has needs_crop=true
  • Dataset with 5 landscape (1920×1080) + 5 portrait (720×1280) at resolution=1024: two buckets; landscape maps to ~1024x576, portrait to ~576x1024
  • Dataset folder does not exist: route returns 404
  • PIL fails on a corrupt image: script logs a warning and skips the file; other images still return correctly
  • Empty dataset folder: returns {images: [], buckets: {}} with 200 status
  • resolution=512, divisibility=64: buckets are multiples of 64; verify against manual calculation

Verification

Call the route via curl against a real dataset folder; compare bucket counts to what the trainer reports in its log after latent caching with the same resolution.

U2 Focal point detection — SSE route

Goal

For a list of image paths that need cropping, call the configured vision LLM once per image to detect the focal point (3×3 grid position), stream one SSE event per image as results arrive, and fall back to center on any failure.

Dependencies

None — can build in parallel with U1.

Files

  • ui/src/app/api/datasets/focal-points/route.ts

Approach

  • Method: POST. Body: {imagePaths: string[]} (absolute paths from the scan result)
  • Read LLM config via getCheckConfigApiBaseUrl(), getCheckConfigApiKey(), getCheckConfigModel(). If base URL is empty, emit center for all images immediately and close the stream.
  • Returns Content-Type: text/event-stream; charset=utf-8 with Cache-Control: no-cache
  • For each image (sequential, not parallel — Ollama handles one vision request at a time reliably):
    1. Read file from disk as Buffer, convert to base64 data:image/jpeg;base64,…
    2. Call openai.chat.completions.create with the multimodal message:
      • System: "You detect the position of the main subject in images. Reply with ONLY one of these exact words: top-left, top-center, top-right, center-left, center, center-right, bottom-left, bottom-center, bottom-right. No other text."
      • User: [{type: "image_url", image_url: {url: dataUrl}}, {type: "text", text: "Where is the main subject?"}]
    3. Parse response — strip whitespace, lowercase, check against the 9 valid values. If invalid or API error, use center
    4. Emit SSE event: data: {"path":"...","anchor":"top-left","source":"ai"|"fallback"}\n\n
  • Emit final event: data: {"done":true}\n\n then close the stream
  • Resize images to max 512px on the long side before base64 encoding — reduces API payload dramatically while retaining enough information for subject position detection

Patterns to follow

ui/src/app/api/jobs/check-config/route.ts — OpenAI SDK setup, getCheckConfigApiBaseUrl() usage, multimodal content array. ui/src/app/api/scripts/route.ts runStreaming — ReadableStream constructor + TextEncoder pattern for SSE.

Test scenarios

  • API base URL not configured: all images receive center fallback immediately; stream closes with done
  • Valid vision model + 3 images: stream emits 3 data events then done; each event has path, anchor, and source:"ai"
  • Model returns "bottom right" (with space, wrong format): route normalizes to bottom-right correctly; if normalization fails, falls back to center
  • LLM API returns 400/500: image gets center fallback + source:"fallback"; stream continues with remaining images
  • Image file does not exist (path stale): skip with fallback, log warning, continue
  • 5-image dataset: progress arrives sequentially, not batched; each event appears within ~2 s of the previous

Verification

Call the route with 3–5 real images from a dataset where the subject position is obvious (clear portrait, clear landscape subject). Confirm the AI-detected anchor matches human expectation for at least 3/5 images with Qwen3-VL-8B.

U3 Crop/resize Python script + processing API route

Goal

Python script that processes a dataset to a new folder using per-image crop anchor decisions, with streaming NDJSON progress. API route that invokes it and relays the stream to the UI.

Dependencies

U1 (output folder naming established by the API route, which extends the U1 pattern).

Files

  • ui_scripts/crop_resize_dataset.py
  • ui/src/app/api/datasets/[datasetName]/process-buckets/route.ts

Approach

Python script (ui_scripts/crop_resize_dataset.py):

  • CLI args: --input-dir PATH, --output-dir PATH, --resolution INT, --divisibility INT, --mode resize|crop, --decisions PATH (path to a JSON file with {absoluteImagePath: {anchor_x: float, anchor_y: float}})
  • Creates output dir if missing
  • For each image:
    • resize mode: compute bucket via get_bucket_for_image_size, then resize with Image.LANCZOS to fit within the bucket — scale by min(target_w/w, target_h/h) so image fits without cropping, preserving aspect ratio. Final size may not exactly equal bucket dims; trainer handles this.
    • crop mode: compute bucket, apply mnslarcher-style resize-then-crop with anchor offset: resize so the short side matches target, then left = int(excess_w * anchor_x), top = int(excess_h * anchor_y); look up (anchor_x, anchor_y) from decisions dict; default to (0.5, 0.5) if image not in dict
  • Save output image preserving original format (.jpg → .jpg, .png → .png); convert RGBA→RGB before saving as JPEG
  • Copy sidecar caption files: for each of .txt, .json, .caption that exist alongside the source image, copy to output dir with same stem
  • After each image, emit NDJSON progress: {"type":"progress","current":N,"total":M,"name":"filename.jpg"}
  • On completion, emit {"type":"done","output_dir":"/abs/path/to/output","total":M,"skipped":K} as the final stdout line
  • On per-image error: emit {"type":"warning","name":"file.jpg","error":"..."} and continue

API route (POST /api/datasets/[datasetName]/process-buckets):

  • Body: {resolution, divisibility?, mode: "resize"|"crop", decisions: {[path]: {anchor_x, anchor_y}}}
  • Resolves output dir: {datasetsRoot}/{datasetName}_bucket_{W}x{H} where W×H is the target bucket at the given resolution for a 1:1 image. Appends _2, _3, etc. if folder already exists.
  • Writes the decisions object to a temp file (os.tmpdir()/decisions-{uuid}.json)
  • Spawns the Python script in streaming mode (same as /api/scripts runStreaming) and returns the ReadableStream response with NDJSON content-type
  • Cleans up the temp JSON file in the stream's cancel() callback

Patterns to follow

ui/src/app/api/scripts/route.ts — runStreaming function exactly. mnslarcher's resize_and_crop.py for the crop math (borrow, then add anchor offset). toolkit/buckets.py get_bucket_for_image_size for bucket assignment.

Test scenarios

  • Resize mode, 10 images: all 10 emitted as progress events; output images are smaller but preserve aspect ratio; no crop artifacts
  • Crop mode, anchor=center (0.5, 0.5): output matches mnslarcher's center-crop output for same inputs
  • Crop mode, anchor=top-left (0.0, 0.0) for a wide image: output keeps left portion, discards right — verify with PIL crop coordinates in test
  • Output folder already exists: route appends _2 suffix; script creates the new folder
  • Image has RGBA mode (PNG with alpha): saved as JPEG without error (RGB conversion applied)
  • Caption sidecar present (.txt): copied alongside output image
  • Caption sidecar absent: no error, no empty file created
  • Script receives a corrupt image: emits warning NDJSON, continues to next image; final done event reflects correct skipped count

Verification

Run the script directly from WSL on a test dataset with known anchors. Inspect output images visually and verify the correct sides are cropped. Confirm caption files copied. Confirm NDJSON progress lines are valid JSON.

U4 BucketToolsModal — all five steps

Goal

Single multi-step modal component managing the full bucket consolidation workflow: scan, configure, detect, review, process, done.

Dependencies

U1, U2, U3 (all routes must exist before the UI can call them).

Files

  • ui/src/components/BucketToolsModal.tsx

Approach — Step 1: Scan + Configure

  • On open: immediately call POST /api/datasets/[datasetName]/scan-buckets with default resolution 1024. Show a spinner while scanning.
  • On result: display a bar-style bucket distribution — each bucket as a labeled bar showing WxH: N images. Highlight buckets with <10 images in amber.
  • Resolution presets: 512, 768, 1024 (default), 1280, custom. Changing the preset re-calls the scan route and re-renders the distribution.
  • Mode picker: "Resize only" (radio) vs "Crop to ratio" (radio). Resize-only note: "Images keep their original aspect ratio — trainer handles multiple sizes within the pixel budget."
  • "Continue" button advances to Step 2 (crop mode) or Step 4 (resize mode). Disabled while scanning.

Approach — Step 2: Focal point detection

  • Show only images where needs_crop: true (from scan result). If zero such images, skip directly to Step 3 (review, showing only the resize-only count).
  • Connect to POST /api/datasets/focal-points via fetch() + response.body.getReader() + TextDecoder. Parse SSE data: lines as JSON.
  • Show a progress bar: "Detecting focal points: N / M images". Each SSE event increments the counter and adds the result to a decisions state map.
  • While detecting: show a "Skip detection (use center crop)" button that aborts the fetch reader, fills remaining images with center anchor, and advances to Step 3.
  • If no LLM configured: skip this step automatically with a banner "No vision model configured — defaulting to center crop. You can override below."

Approach — Step 3: Per-image review grid

  • Grid of thumbnail cards — only images with needs_crop: true. Images that only need resizing appear as a summary line: "N images will be resized (no crop needed)."
  • Each card (approx. 200px wide):
    • Shows the image via the existing /api/img/[...imagePath] route (the same route used by DatasetImageCard)
    • Overlays the crop region using an absolutely-positioned div with clip-path: the overlay is rgba(0,0,0,0.55) with a "hole" cut at the kept crop rectangle. The hole's position and size are computed from the anchor (anchor_x, anchor_y) and the image's aspect ratio vs. target aspect ratio.
    • Shows the AI anchor label: "AI: top-left" or "Fallback: center"
    • 3×3 button grid picker below the thumbnail: 9 small buttons (grid CSS) labelled with arrows or position names. Active button highlighted in blue. Clicking updates decisions[imagePath] state.
  • Crop overlay CSS clip-path formula (directional, not code): outer polygon covers 0%–100% of both axes; inner "hole" polygon is defined by the crop rectangle as percentages: left%=(anchorX × (1 - cropW/origW) × 100), top%=(anchorY × (1 - cropH/origH) × 100), right%=left%+(cropW/origW × 100), bottom%=top%+(cropH/origH × 100). Winding rule: outer clockwise, inner counter-clockwise.
  • "Process N images" button at the bottom of Step 3 advances to Step 4.

Approach — Step 4: Processing

  • On enter: call POST /api/datasets/[datasetName]/process-buckets with {resolution, mode, decisions}. The decisions object is {[absolutePath]: {anchor_x, anchor_y}} built from the Step 3 state.
  • Read NDJSON stream: each progress event updates a progress bar ("Processing: N / M") and shows the current file name.
  • warning events: collect and display below the progress bar as amber text.
  • On done event: advance to Step 5.

Approach — Step 5: Done

  • Show summary: "Processed M images → {outputDatasetName}". If warnings: "K images had errors (see below)."
  • "Open dataset" button: navigates to /datasets/{outputDatasetName} and closes the modal.
  • "Close" button: closes modal without navigating.

State shape

Key state in the modal component:

  • step: 1|2|3|4|5
  • scanResult: {images, buckets} | null
  • resolution: number
  • mode: "resize"|"crop"
  • decisions: Record<string, {anchor_x: number, anchor_y: number}>
  • detectProgress: {current, total}
  • processProgress: {current, total, warnings: string[]}
  • outputDatasetName: string | null

Patterns to follow

ui/src/components/Modal.tsx — use the existing Modal component with size="xl". ui/src/app/datasets/[datasetName]/page.tsx — apiClient pattern, Button from headlessui, Tailwind classes. The SampleImageViewer fetch-stream pattern for NDJSON if needed. VirtuosoGrid is available for the review grid if image count is large, but plain CSS grid is fine for <200 images.

Test scenarios

  • Step 1 — resolution change from 1024 to 512: re-scan fires and bucket distribution updates; button stays disabled during re-scan
  • Step 1 — resize mode selected: "Continue" → jumps directly to Step 4, no Step 2 or 3
  • Step 2 — 5 images need crop: progress bar reaches 5/5 then auto-advances; "Skip" button aborts mid-detection and fills center
  • Step 3 — user changes anchor from AI suggestion: overlay re-renders showing new crop region; decisions map updated
  • Step 3 — all images have same aspect ratio as target (no crop needed): no images shown in grid; "0 images need cropping" label shown; Process button visible
  • Step 4 — NDJSON warning emitted by script: amber warning text appears below progress bar
  • Step 5 — "Open dataset" click: navigates to /datasets/{name}
  • Modal escape/backdrop close: if processing (Step 4), confirm dialog first; otherwise close freely

Verification

Open modal on a dataset with mixed aspect ratios. Walk through all 5 steps with a real Ollama vision model. Confirm crop overlays match the selected anchor visually. Confirm the output folder contains correctly processed images and caption sidecars.

Open Questions / Deferred to Implementation

Deferred to implementation
needs_crop threshold — how much aspect ratio difference warrants a crop warning vs treating as "resize only". Suggest: if |bucket_ar - image_ar| / image_ar > 0.02 (2% relative difference) then needs_crop=true. Tune during implementation.
Deferred to implementation
Review grid virtualization — if a dataset has >200 images needing crop, the review grid could be slow. Implement as plain CSS grid first; add react-virtuoso (already installed) if render time is noticeable during testing.
Deferred to implementation
Resize-mode output size — in resize-only mode, should output images be scaled to exactly the bucket WxH (with padding/letterboxing) or to "fit within" (shorter dimension may not reach the target)? Plan says "fit within" (no padding). If padding is ever wanted, that's a new mode.
Deferred to implementation
Confirm close during processing — if user presses Escape or clicks backdrop during Step 4, add a "Processing is running. Close anyway and continue in background?" confirmation. Implement with a simple window.confirm in the modal's onClose guard.
Deferred to implementation
LLM response normalization — some models return "The subject is in the top-left" instead of just "top-left". Add a simple regex search for the 9 valid anchor strings before declaring a fallback. If found anywhere in the response, use it.
